# StudyForge — Application Inspection Report

*Date: 2026-09-25 · Scope: full source under `D:\class 11 app\study fork` (216 source files, ~5,050 lines Motoko backend + ~38,000 lines TypeScript/TSX frontend)*

---

## 1. What this app is

**StudyForge** is a full-stack study platform for organizing and practicing course material, built on the **Caffeine framework for the Internet Computer (ICP)**. It was generated from `@caffeine/template-app` and extended into a class-11-style study tool.

It combines three product areas:

1. **Study tools (core)** — a 4-level content hierarchy (Class → Subject → Chapter → Topic) with MCQ / true-false / short-answer questions, practice sessions with instant feedback, timed tests with auto-submit, and analytics (accuracy by class/subject/question type, attempt history).
2. **AI Studio** — generate draft questions from a prompt or an uploaded document, using either a personal OpenAI key or the Caffeine platform inference service; drafts are reviewed in bulk before being accepted into a topic.
3. **Distribution** — a public dynamic QR-code link shortener with scan analytics, public read-only share links for question sets, a private notes workspace (block editor, autosave, sharing), and CSV/PDF export.

Per `project.json`: *"a study platform with a public dynamic QR code generator, a private notes workspace, and full study tools."*

## 3. Architecture

```
React SPA (src/frontend)
  └─ hooks/useBackend.ts ──► generated Backend actor (Candid)  ──► Motoko canister (src/backend)
        │                                                                └─ main.mo: state + 8 domain mixins
        └─ if VITE_USE_MOCK=true ──► localStorage mock backend (full canister emulation)
```

- **Frontend**: `main.tsx` resolves the backend actor *before* first paint; every domain hook (content, sessions, analytics, notes, QR, sharing, settings, AI) is TanStack Query with a central query-key factory. Signed-in routes nest under a `RequireAuth` shell (header + sidebar).
- **Backend**: `main.mo` (~270 lines) holds all state as stable `let` fields and passes them into eight mixins (`content-api`, `sessions-api`, `analytics-api`, `sharing-api`, `notes-api`, `qr-links-api`, `ai-api`, `api-doc`), each delegating to a pure-ish lib module. A `Expose({...})` block registers 14 OQL entities (controller-only diagnostics queries). A hand-written Markdown API doc is served from the canister (`getApiDoc`).
- **Upgrades**: no explicit `pre/postupgrade`; stability comes from persistent-actor semantics, with a two-step migration chain in `src/backend/migrations/` and a stable-shape check against `.old/src/backend/dist/backend.most`.

## 5. Security & correctness findings (prioritized)

1. **Authentication is dev-only.** The UI guards routes with `src/lib/localAuth.ts` — email/password accounts stored in `localStorage` (PBKDF2 verifier). The file's own header says production must replace it. Internet Identity plumbing exists in the bindings and `@icp-sdk/auth` is installed, but the UI never uses it. On the canister side, every method keys off `caller` principal, so two local accounts on the same browser map to the *same* anonymous principal — data would collide against a real backend.
2. **Predictable content-share tokens.** `sharing.mo:96` mints `sh_<sequential-id>_<timestamp>` — enumerable by anyone who knows the scheme. (Note tokens, by contrast, use a 24-char CSPRNG.)
3. **QR codes/edit tokens use a non-cryptographic PRNG.** `qr-links.mo:55–78` uses a clock-seeded LCG, acknowledged in-comment as "enough for a draft app". QR management is bearer-token only (no principal binding).
4. **OpenAI keys stored in plaintext** in the stable `aiKeys` map (`Map<Principal, Text>`) — recoverable from any canister-state copy; only the masked hint is returned to clients.
5. **O(n) linear scans everywhere.** QR code/token lookup, hierarchy child counts, and analytics ownership derivation iterate full maps per call — fine for a single user, a scalability ceiling for multi-user.
6. **Session-result ownership derives from the *current* topic owner** — deleting (or ever transferring) a topic orphans prior results.
7. **PDF export is single-page** hand-built PDF-1.4 with no pagination — long topic exports are silently clipped.
8. **Global drafts cap**: `ai-api.mo` wipes *all* users' drafts when the shared map exceeds 100 entries.
9. **Housekeeping**: unused heavy deps installed (`three`, `@react-three/fiber/drei/cannon` + types) and unused shadcn scaffolds (`calendar`, `carousel`, `input-otp`, `form`); the two migration files each duplicate ~200 lines of entity types by hand (drift hazard); `resolveCode` counts retries as scans (documented).

## 6. Code quality notes

- Clean layering: thin API mixins over pure-ish libs; generated bindings isolated behind `src/types/index.ts`; a single `useBackend` access point; central query-key factory.
- No TODO/FIXME noise; explanatory doc comments throughout (including a self-documenting canister API doc and a heavily-commented CI gate script).
- Big files to know about: `pages/NoteDetail.tsx` (1,068), `pages/SettingsPage.tsx` (990), `pages/AiStudio.tsx` (799), `pages/QrGenerator.tsx` (761), `lib/content.mo` (606), `lib/notes.mo` (548), `lib/qr-links.mo` (543).
- Build quirks inherited from the template: `vite build` with `minify: false` (ICP asset-size practice), package still named `@caffeine/template-frontend`.

3. Initialize this folder as its own git repository before further changes.
4. Drop the unused 3D dependencies and shadcn scaffolds to slim the install.
5. Add tests for `AuthPage` / `AiSettings` / `SessionResults`.
