# StudyForge auth email templates

The branded versions of the five emails Supabase Auth (GoTrue) sends. Paste each
file's body into the matching template in the project dashboard:

**Authentication → Email Templates → [template]**, and set the subject lines
suggested below. The app renders its own sign-in / verify / reset screens, so
these templates only carry the account action link — they never ask for a
password inside the email itself.

| Template            | File                    | Suggested subject |
|---------------------|-------------------------|-------------------|
| Confirm signup      | `confirm-signup.html`   | `Verify your email to start StudyForge` |
| Reset password      | `reset-password.html`   | `Reset your StudyForge password` |
| Magic link          | `magic-link.html`       | `Your StudyForge sign-in link` |
| Invite user         | `invite.html`           | `You are invited to StudyForge` |
| Change email address| `change-email.html`     | `Confirm your new StudyForge email` |

## How the templates work

- Each body is a complete HTML document with inline styles and table layout —
  the subset of HTML mail clients render reliably. No remote images or fonts,
  which also keeps spam scores low.
- `{{ .ConfirmationURL }}` is the GoTrue-built action link. It must stay the
  `href` of the button **and** the visible fallback link: it carries the token
  that the app's session layer (supabase-js `detectSessionInUrl`) consumes
  when the user lands back on the app.
- `{{ .Email }}` personalizes the copy; `change-email.html` also uses
  `{{ .NewEmail }}`; the footers link `{{ .SiteURL }}` back to the app. All
  variables are escaped by GoTrue, so pasting user-controlled text is safe.
- The design matches the daily digest email (same gradient header, card and
  palette) generated by `buildDigestHtml` in
  `src/frontend/src/lib/reminders.ts`. Keep the two visually in step when one
  changes.

## Prerequisites on the Supabase side

1. **Authentication → URL Configuration → Site URL** must be the deployed app
   origin (the Vercel URL — see `DEPLOY.md`), and
   `Additional redirect URLs` should allow the same origin, so the
   confirmation link can land the user back in the app to complete
   verification.
2. **Authentication → Sign In / Providers**: only Email is used; the templates
   above cover every email the project sends.
3. **Authentication → SMTP settings** decides whether these templates ever
   reach anybody. On the built-in sender they are capped at two messages an
   hour, leave from a shared `*.supabase.co` address, and Gmail files them
   under Spam — so a correctly pasted template can still look like "the
   verification email never came". Saving the settings does not test them: the
   failure only surfaces on the next request. Route them through your own
   verified domain first; the field values and the SMTP-key-vs-API-key trap are
   in `../README.md` → *Sending auth mail through an SMTP relay*, and
   `../e2e/auth-mail-check.mjs` proves which side failed.
4. If a template is edited in the dashboard later, copy the change back into
   the matching file here — these files are the version of record.
